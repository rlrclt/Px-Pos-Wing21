Standard Mode System Online

1. หมวดหมู่การออกแบบ UX/UI (UX/UI Design)

impeccable

สถานการณ์ (Trigger): เมื่อผู้ใช้ต้องการออกแบบ, ปรับปรุง, ตรวจสอบ, หรือขัดเกลาหน้าตาของ User Interface (UI) ให้มีความเป็นมืออาชีพ ไม่ว่าจะเป็นเว็บไซต์, แดชบอร์ด, หรือคอมโพเนนต์ต่างๆ

การทำงาน (Action): Agent จะใช้หลักการออกแบบ Frontend ที่มีความละเอียดอ่อน (Craft) เพื่อขจัดหน้าตาแบบ AI Slop (เช่น สีม่วง/ฟ้าเรืองแสง) และสร้าง Design System ที่แข็งแรง ทั้งในเรื่องของสี, Typography, การจัดวาง, และแอนิเมชัน ให้ได้งานที่ใช้งานได้จริงและสวยงาม

2. หมวดหมู่การวางแผน (Planning)

handoff

สถานการณ์ (Trigger): เมื่อกำลังจะจบเซสชั่นการทำงานปัจจุบัน, รันคำสั่งครบข้อจำกัด, หรืองานมีความซับซ้อนมากจนต้องส่งต่อบริบทให้ Agent ตัวถัดไปมารับช่วงต่อ

การทำงาน (Action): สร้างหรืออัปเดตไฟล์เอกสาร `HANDOFF.md` อย่างละเอียด โดยบันทึกความคืบหน้าของงาน, สิ่งที่ทำสำเร็จ, ปัญหาหรือบั๊กที่ยังแก้ไม่ตก, และเป้าหมาย/ขั้นตอนที่ต้องทำต่อไป เพื่อให้ Agent ตัวใหม่มีข้อมูลครบถ้วนโดยไม่ต้องเริ่มใหม่

brainstorming

สถานการณ์ (Trigger): เมื่อเผชิญกับโปรเจกต์ใหม่, ฟีเจอร์ใหม่, หรืองานที่ต้องการความคิดสร้างสรรค์ ซึ่งยังไม่มีข้อกำหนด (Requirements) หรือแนวทางที่ชัดเจน

การทำงาน (Action): Agent จะตั้งคำถามเจาะลึกเพื่อสำรวจความต้องการของผู้ใช้, ค้นหาไอเดียทางเลือก, ประเมินความเสี่ยง, และร่วมกันร่างโครงสร้างสถาปัตยกรรม (Architecture) จนกว่าจะได้ภาพรวมที่ชัดเจนและได้รับการอนุมัติ

writing-plans

สถานการณ์ (Trigger): เมื่อมีเป้าหมาย, ข้อกำหนด (Spec), หรือผลลัพธ์จากการ brainstorm ที่ชัดเจนแล้ว แต่ยังไม่มีขั้นตอนการลงมือทำที่ชัดเจน (ยังไม่พร้อมเขียนโค้ด)

การทำงาน (Action): วิเคราะห์ความต้องการและแตกงานใหญ่ออกเป็น "แผนการทำงานแบบเป็นขั้นตอน" (Step-by-step Execution Plan) ที่ละเอียด, มีลำดับการทำงานที่ถูกต้อง, และมีจุดเช็คพอยต์ (Checkpoints) สำหรับตรวจสอบความถูกต้องในแต่ละระยะ

dispatching-parallel-agents

สถานการณ์ (Trigger): เมื่อในแผนงานมีงานย่อยหลายงานที่เป็นอิสระต่อกัน (Independent tasks) ไม่มีการใช้ตัวแปรร่วมกัน และไม่ต้องรอให้อีกงานเสร็จก่อน

การทำงาน (Action): กระจายงานเหล่านั้นให้กับ Subagent หลายๆ ตัวทำงานไปพร้อมๆ กัน (Parallel execution) เพื่อประหยัดเวลาอย่างมหาศาล โดยคอยติดตามสถานะและรวบรวมผลลัพธ์

using-git-worktrees

สถานการณ์ (Trigger): เมื่อต้องเริ่มงานฟีเจอร์ใหม่หรือทดลองแก้โค้ดที่อาจทำให้โค้ดหลักพัง และต้องการสภาพแวดล้อมที่แยกตัวออกมา (Isolation)

การทำงาน (Action): ตรวจสอบสถานะของ Repository ปัจจุบัน และใช้คำสั่งสร้าง Git Worktree (หรือ Branch ใหม่ถ้าจำเป็น) เพื่อให้สามารถเขียนโค้ดและทดสอบได้อย่างอิสระ โดยไม่กระทบโฟลเดอร์หลัก

3. หมวดหมู่การลงมือพัฒนา (Development & Execution)

executing-plans

สถานการณ์ (Trigger): เมื่อมีไฟล์แผนการทำงาน (Plan) ที่เขียนไว้อย่างชัดเจน และพร้อมที่จะลงมือเขียนโค้ดในเซสชั่นใหม่

การทำงาน (Action): ดำเนินการเขียนโค้ดตามแผนทีละขั้นตอนอย่างเคร่งครัด พร้อมทั้งหยุดรายงานผลและขอการอนุมัติ (Review checkpoints) จากผู้ใช้เมื่อจบแต่ละขั้นตอนสำคัญ เพื่อให้มั่นใจว่ามาถูกทาง

subagent-driven-development

สถานการณ์ (Trigger): เมื่อมีแผนการทำงานที่ประกอบด้วย Task ย่อยหลายอย่างในเซสชั่นปัจจุบัน และการทำคนเดียวอาจใช้เวลานานหรือกินบริบท (Context) มากเกินไป

การทำงาน (Action): เรียกใช้ Subagent มารับหน้าที่เขียนโค้ดหรือตรวจสอบการทำงานในแต่ละส่วนแยกกัน โดย Agent หลักจะทำหน้าที่เป็นผู้จัดการ (Manager) คอยแจกจ่ายงานและตรวจสอบโค้ด

test-driven-development

สถานการณ์ (Trigger): เมื่อต้องเริ่มต้นเขียนโค้ดฟีเจอร์ใหม่, สร้างคอมโพเนนต์ใหม่, หรือกำลังจะแก้ไขบั๊กที่มีการรายงานเข้ามา

การทำงาน (Action): บังคับใช้กระบวนการ TDD อย่างเคร่งครัด โดยจะต้องเขียนเทสต์ (Unit/Integration) ให้ล้มเหลว (Red) ก่อน จากนั้นจึงเขียนโค้ดจริงเพื่อให้เทสต์ผ่าน (Green) และ Refactor ในที่สุด

4. หมวดหมู่การตรวจสอบและแก้ปัญหา (Review & Debugging)

systematic-debugging

สถานการณ์ (Trigger): เมื่อเจอบั๊ก, เทสต์พัง, หรือระบบแสดงพฤติกรรมที่ไม่คาดคิด และยังไม่ทราบสาเหตุที่แน่ชัด

การทำงาน (Action): สั่งห้ามการเดาสุ่มแก้โค้ดหรือลองผิดลองถูก Agent จะต้องรวบรวมข้อมูล, วิเคราะห์ Log, ตรวจสอบสมมติฐาน, และหา "ต้นตอ" (Root cause) ของปัญหาให้เจอก่อนเสมอ

requesting-code-review

สถานการณ์ (Trigger): เมื่อพัฒนางานชิ้นใหญ่เสร็จสิ้น, ทำตามแผนจนครบ, หรือเตรียมพร้อมที่จะดึงโค้ด (Merge) เข้าสู่ Main Branch

การทำงาน (Action): ร้องขอให้ผู้ใช้หรือ Agent ตัวอื่นทำการรีวิวโค้ดอย่างละเอียด โดยนำเสนอรายการสิ่งที่เปลี่ยนแปลง เหตุผลในการตัดสินใจ และจุดที่อาจต้องระวัง เพื่อให้มั่นใจในคุณภาพ

receiving-code-review

สถานการณ์ (Trigger): เมื่อได้รับข้อเสนอแนะ (Feedback) หรือคอมเมนต์จากการรีวิวโค้ด (PR Comments)

การทำงาน (Action): รับข้อเสนอแนะมาวิเคราะห์ด้วยความรอบคอบทางเทคนิค ไม่แก้ตามทันทีแบบหลับหูหลับตา หากคอมเมนต์ขัดแย้งกับหลักการจะอธิบายชี้แจง แต่หากถูกต้องจะดำเนินการแก้ไข

verification-before-completion

สถานการณ์ (Trigger): เมื่อ Agent คิดว่างานเสร็จแล้ว และกำลังจะพิมพ์ตอบผู้ใช้ว่า "แก้ไขเรียบร้อยแล้ว"

การทำงาน (Action): กฎเหล็กที่บังคับให้ Agent ต้องรันคำสั่งตรวจสอบ (เช่น สคริปต์เทสต์ หรือ Lint) และต้องเห็นผลลัพธ์ว่า "ผ่าน" จริงๆ ก่อนที่จะกล้าประกาศความสำเร็จ ห้ามใช้การคาดเดา

finishing-a-development-branch

สถานการณ์ (Trigger): เมื่องานใน Branch ปัจจุบันเสร็จสมบูรณ์ 100%, ผ่านการเทสต์, และผ่านการรีวิวเรียบร้อยแล้ว

การทำงาน (Action): ช่วยผู้ใช้จัดการขั้นตอนปิดจ๊อบ เช่น การคลีนโค้ด, การเขียน Commit message ที่ได้มาตรฐาน, และช่วยตัดสินใจวิธีรวมโค้ด (Merge) กลับเข้าสู่ Main Branch อย่างปลอดภัย

5. หมวดหมู่ระบบและการสื่อสาร (System & Interaction)

using-superpowers

สถานการณ์ (Trigger): ทันทีที่เริ่มต้นบทสนทนาใหม่ในทุกๆ ครั้ง

การทำงาน (Action): เป็นข้อบังคับระดับระบบที่ให้ Agent ตรวจสอบและดึงทักษะพิเศษ (Skills) หรือเอกสารคู่มือมาอ่านก่อนที่จะไปลงมือทำแอคชั่นอื่นๆ

caveman

สถานะปัจจุบัน (Default): เปิดใช้แบบ `full` อัตโนมัติทุก session ไม่ต้องพิมพ์ `/caveman`

การทำงาน (Action): บีบอัดคำตอบ ตัดคำเยิ่นเย้อ คำทักทาย และการรายงาน progress แต่เก็บข้อมูลเทคนิค คำสั่ง ตัวเลข error และข้อควรระวังไว้ครบ ใช้ `normal mode`, `stop caveman` หรือ `/caveman off` เพื่อปิด

agy-customizations

สถานการณ์ (Trigger): เมื่อผู้ใช้มีคำถาม หรือต้องการปรับแต่งระบบ Antigravity ด้วยตัวเอง

การทำงาน (Action): เปิดอ่านคู่มือเชิงลึกที่อธิบายกลไก เพื่อนำทางผู้ใช้ในการสร้าง Skills, Rules, Plugins, Hooks, หรือเชื่อมต่อ MCP Servers เข้ากับระบบ

antigravity-guide

สถานการณ์ (Trigger): เมื่อผู้ใช้มีคำถามพื้นฐานเกี่ยวกับการใช้งานระบบ Antigravity (AGY)

การทำงาน (Action): ใช้เอกสารคู่มือและแผนผังเว็บไซต์รวม (Sitemap) ของ Antigravity CLI, IDE, Python SDK และคำสั่งลัดต่างๆ เพื่อตอบข้อสงสัย

writing-skills

สถานการณ์ (Trigger): เมื่อผู้ใช้ต้องการให้สร้างไฟล์คำสั่ง Skill ใหม่ หรือแก้ไขปรับปรุงของเดิม

การทำงาน (Action): แนะนำรูปแบบ โครงสร้าง แนวทางปฏิบัติที่ดีที่สุด (Best practices) และวิธีการทดสอบ เพื่อให้แน่ใจว่าไฟล์ Skill ที่สร้างใหม่ระบบสามารถอ่านได้

6. Gemini ที่จูนไว้ และวิธีเริ่มใช้

สิ่งที่จูนแล้ว

  • ตอบสั้น: ใช้ caveman full ทุก session และไม่รายงานขั้นตอนระหว่างทำงาน
  • ทำงานรอบคอบ: อ่านโค้ดก่อนแก้ ใช้ skill ตามชนิดงาน และไม่อ้างผลทดสอบที่ยังไม่ได้รัน
  • ตรวจจบงาน: รัน test หรือ build ที่เกี่ยวข้องก่อนสรุปผล
  • ตอบไทย: ตามภาษาที่ผู้ใช้พิมพ์ โดยเก็บคำสั่งและศัพท์เทคนิคให้ตรงต้นฉบับ

Agents ที่เพิ่ม

  • @task-planner วางแผนงานใหญ่โดยไม่แก้ไฟล์
  • @code-implementer ลงมือแก้แบบ scope เล็กและทดสอบ
  • @bug-investigator หาต้นตอ bug พร้อมหลักฐาน
  • @quality-reviewer รีวิวความถูกต้อง ความเสี่ยง และ test gap
  • @ui-ux-reviewer ตรวจ usability, responsive และ accessibility

ไฟล์ที่ต้องมี

~/.gemini/GEMINI.md
Global entry point; import กติกาและ caveman

~/.gemini/config/GEMINI.md
กติกาการทำงาน global

~/.gemini/agents/*.md
Agent definitions ทั้ง 5 บทบาท

.gemini/GEMINI.md
กติกาเฉพาะโปรเจกต์ เช่น POS, sync และ test

เปิดใช้ครั้งแรก หรือหลังแก้ config

  1. เปิด Gemini CLI หรือ Antigravity ที่โฟลเดอร์โปรเจกต์
  2. พิมพ์ /memory reload เพื่ออ่าน global และ project instructions ใหม่
  3. พิมพ์ /agents reload เพื่อโหลด custom agents ใหม่
  4. พิมพ์ /agents list แล้วตรวจว่ามี agent ทั้ง 5 ตัว
  5. ลองใช้ เช่น @task-planner วางแผนเพิ่มระบบส่วนลดสินค้า

ย้ายไป Gemini เครื่องหรือบัญชีใหม่

  1. ติดตั้งและลงชื่อเข้าใช้ Gemini CLI/Antigravity ให้เรียบร้อย
  2. คัดลอกโฟลเดอร์ ~/.gemini/agents/ และไฟล์ global ทั้งสองรายการไปยัง home directory ของบัญชีใหม่
  3. คัดลอก .gemini/GEMINI.md ไปพร้อม repository หากต้องการกติกาเฉพาะโปรเจกต์
  4. เปิด session ใหม่ แล้วรัน /memory reload, /agents reload, และ /agents list

ถ้าไม่เห็น agent: ตรวจ path, ชื่อไฟล์ .md, YAML frontmatter ที่ขึ้นต้นและปิดท้ายด้วย ---, แล้ว reload อีกครั้ง

7. แนะนำคอมโบการทำงาน (Workflow Combos)
